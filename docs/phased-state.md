# Phased 승인 상태 계약

이 문서는 Phased 문서의 승인 상태와 갱신에 따른 무효화를 공통으로 정의한다. `spec-init`, `design-init`, `implement-init`, `implement`, `implement-loop`, `verify`는 이 문서를 직접 읽고 각 단계의 작성·검증 규칙을 함께 적용한다.

## 상태 계산

- `SPEC`은 현재 `spec.md`에 미확정 요구사항이 없고 사용자가 승인한 요구사항과 일치할 때 `[x]`다.
- `DESIGN`은 현재 적용 중인 모든 `SPEC §5.N`을 충족하는 설계가 확정되고 미채택 결정이 없을 때 `[x]`다.
- `IMPLEMENT`는 현재 적용 중인 각 `SPEC §5.N`이 하나 이상의 Task에 매핑되고 그 매핑 Task가 모두 현재 기준으로 승인됐을 때만 `[x]`다. 구현 완료 검증과 Task 승인·거절은 `verify`의 판정 계약을 따른다.
- spec 변경으로 일부 설계가 무효가 되어 `DESIGN`이 `[ ]`여도 영향 없는 Task의 `[x]`는 보존할 수 있다. 미해결 설계가 남은 동안 새 구현에는 진입하지 않는다.

## 갱신과 무효화

- 상태와 승인은 문서 전체 재작성 여부가 아니라 현재 내용의 의미와 의존 관계로 판단한다. 오탈자·표현·링크·형식처럼 요구사항·설계·Task 경계·검증 기준의 의미를 바꾸지 않는 편집은 main이 변경 전후 의미가 같다는 근거를 확인한 뒤 기존 승인을 유지할 수 있다.
- 요구사항, 설계, Task 경계나 검증 기준이 바뀌면 영향받는 설계·Task와 그 의존 Task만 승인 취소한다. 영향 범위를 신뢰성 있게 한정할 수 없으면 해당 단계 아래의 승인을 모두 취소한다.
- 의미 변경인데 승인을 유지하려면 영향 없음이 확인되는 문서·참조·검증 근거가 필요하다. 기존 구현이 남아 있어도 승인이 취소된 Task는 현재 기준으로 다시 검증한다.
- 부분 갱신은 기존 Task의 `시도`와 `최근 reject`를 초기화하지 않는다. 완료 조건은 재배열·재번호하지 않고, Task ID는 재번호하거나 삭제된 ID를 재사용하지 않는다. Task 의존 순서는 `implement-init` 기준에 따라 항목 위치로 조정할 수 있다.
- main은 문서 갱신 때 변경 이유, 승인 취소 대상, 유지한 승인과 근거를 기능 `README.md` 이력에 기록한다. 과거 완료 Task의 승인 근거를 현재 상태에서 추정해 새로 만들지 않는다.
