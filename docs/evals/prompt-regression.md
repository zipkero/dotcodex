# 프롬프트 회귀 평가

## 목적과 적용 범위

설정 지침이 실제 소비 모델과 역할에 맞고, 중복·모호함을 줄이면서 사용자 정책과 역할·승인 계약을 유지하는지 확인한다.
이 문서는 평가자가 설정 변경을 검증할 때 읽는 기준이며, 일반 작업의 AGENTS.md나 skill 입력에 항상 추가하지 않는다.
실제 사용자 프로젝트 대신 폐기 가능한 복사본을 사용하고 운영 접근, 실제 외부 API 호출, 인증 정보 변경은 하지 않는다.

이번 변경의 기준은 `6639fa55f90b127abe031dfe8f2002a685a7bff0`이다.
역할별 참조 분리, 진행 경계 보완과 문구 정리를 구분할 수 있도록 비교 대상의 diff를 보존한다.
이 문서의 시나리오와 기대 결과는 평가 설계이지 실행 완료 기록이 아니다. 실행 여부와 결과는 해당 평가 기록에서 확인한다.

## 정적 검사

비교할 기준과 후보 commit을 먼저 고정한다. 후보에 미커밋 변경이 있으면 staged·unstaged diff와 새 파일도 함께 보존한다.
저장소 루트에서 다음을 확인한다.

```sh
BASE=6639fa55f90b127abe031dfe8f2002a685a7bff0
# 후보 브랜치를 checkout한 뒤 실행한다.
git status --short
git diff --check "$BASE"
git diff --name-status "$BASE"
git diff "$BASE" -- AGENTS.md agents skills README.md docs/evals
```

- 변경한 SKILL.md의 YAML frontmatter와 agent TOML을 파싱한다. 모델·추론·sandbox 설정을 기준 commit과 대조한다.
- 저장소 탐색용 상대 Markdown 링크는 문서 위치를 기준으로 확인한다. 에이전트용 `~/.codex/...` 참조는 홈 디렉터리를 확장해 실제 관리 파일과 대조한다.
  다른 프로젝트의 작업 디렉터리에서도 같은 전역 파일을 읽는지 확인하며, 프로젝트 산출물의 상대 경로를 전역 경로로 바꾸지 않는다.
- main·worker·verifier·감사자의 역할별 참조를 따라 필수 계약이 누락되거나 다른 역할의 실행을 강제하지 않는지 확인한다.
  main·worker의 공통 구현 기준과 역할 전용 계약도 대조한다.
- `git ls-files`와 `git check-ignore --no-index`로 새 references와 docs/evals가 추적 허용 범위인지 확인한다.
- 모든 기존 파일이 보존되고 승인 범위 밖 변경이 없는지 확인한다. 모델·추론 설정과 openai.yaml 호출 정책은 유지한다.
  description은 이름·용도·적용 경계를 대조하며, 단순 축약과 호출 범위 변경을 구분한다.
- 검증 근거 재사용 조건에 현재 코드·테스트·미커밋 diff 확인이 있고, 수동 확인이 필수 테스트를 대체하지 않는지 확인한다.

정적 검사는 실제 skill 선택, subagent 호출 성공, 비용·시간·질문 빈도의 개선을 증명하지 않는다.

## 실제 비교 실행 준비

1. 동일한 fixture 원본을 기준·후보용으로 각각 복사한다. 한 실행의 수정·체크박스·로그가 다음 실행에 남지 않도록 매회 초기화한다.
2. 실제 사용하는 Codex 버전, main 모델·추론 수준, custom agent 설정, 도구·권한, 활성 skill 목록과 프로젝트 지침을 기록한다.
   main 모델을 저장소에서 추정하지 않는다. 기존 런타임이 지원하는 격리된 설정 환경을 사용하며 실제 사용자 전역 설정을 덮어쓰지 않는다.
   전역 참조가 해당 기준·후보의 격리된 설치 루트로 연결되는지도 확인한다. 복사본을 평가하면서 실제 사용자 설정을 읽은 실행은 비교 근거로 쓰지 않는다.
3. 같은 입력과 시작 상태에서 기준·후보를 새 세션으로 실행한다. 가능한 경우 각 조건을 3회 이상 반복하고 순서를 교대로 배치한다.
4. 조회·호출·검증 명령·질문·최종 diff·문서 상태를 실제 기록으로 수집한다. 확인할 수 없는 토큰·로딩 값은 `미확인`으로 적고 0으로 집계하지 않는다.
5. 환경이나 모델·권한이 달라진 실행은 따로 표시하고 지침 변경만의 효과로 해석하지 않는다.

## 로딩·라우팅 관찰

- Per-Request main: 공통 구현 기준과 worker 계약을 사용해 위임 입력과 반환 근거를 검토하며 구현 원본을 직접 수정하지 않는다.
- Per-Request worker: 공통·worker 기준과 필요한 프로젝트·언어·원본을 사용하고 main 절차는 재실행하지 않는다.
- Per-Request verifier: acceptance를 적용하고 Phased 전용 매핑·상태 절차는 실행하지 않는다. Phased 지침 자체가 변경 대상인 경우에는 그 diff를 확인한다.
- Phased verifier: acceptance와 phased의 입력·판정 기준을 읽는다. 파일과 상태는 변경하지 않는다.
- 단순 설정 감사: structure를 사용한다. 전체 감사 또는 모델·하네스 관련 판단에는 model-harness를 추가한다.
- 위 관찰은 이번 변경에 의한 추가 로딩을 대상으로 한다. 런타임이 이미 주입한 전역 지침까지 전혀 보지 않았다고 추정하지 않는다.

12개 관리 skill의 description을 용도와 구분 조건 중심으로 축약했다. 실제 선택 동작은 R20 등을 사용해 description만 별도 비교한다.
프로젝트 문서 템플릿 분리와 모델 교체도 이번 비교에 함께 넣지 않는다.

## 결과 기록과 채택 기준

실행별로 사례 ID, 기준/후보 commit, 환경, 결과, 근거 위치, 정책 위반, 불필요한 질문, 읽은 참조,
검증 명령과 중복 사유, 조기 종료, 실제 소요·토큰(관측 가능할 때)을 기록한다. fixture와 대화 전문의 비밀값은 공유하지 않는다.

- 모든 필수 계약을 지킨 후보만 채택 대상이다. 범위 축소·검증 없는 완료·역할 우회는 비용 절감과 무관하게 실패다.
- 개선 여부는 모델·역할 적합성, 불필요한 절차와 중복, 판단의 명확성으로 평가한다. 분량 증감 자체를 성공이나 실패로 판정하지 않는다.
- 비용·로딩·질문 개선은 실제 비교 기록으로만 판단한다. 파일 바이트 감소만으로 실행 성능 향상을 선언하지 않는다.
- 실패하면 원인이 참조 누락인지 진행 경계 변화인지 분리해 해당 변경을 수정·재평가한다. 반복 실패를 통과시키려고 기대 결과를 완화하지 않는다.
- 실제 비교를 못 했으면 `정적 검토 완료 / 실제 Codex 비교 미실행`으로 보고하고 제거 안전성·성능 개선을 확정하지 않는다.
