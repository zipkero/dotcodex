# Codex 전역 설정 조정 설계

## 근거

- 2026-08-28 Claude 전역 설정의 `CLAUDE.md`는 `Phased` 권장 조건을 구현 전에 확정해야 하는 설계 선택, 되돌리기 어려운 변경, 이후 확인할 완료 조건·영향 범위로 좁히고, 완료·검증 단위가 여럿인 것만으로는 `Phased`를 권장하지 않는 기준을 둔다.

- OpenAI 공식 문서에 따르면 전역 `AGENTS.md`는 세션의 instruction chain에 포함되고 프로젝트 지침과 계층적으로 결합된다. 반면 skill은 우선 metadata만 노출되고 선택된 뒤 `SKILL.md` 본문이 로드된다. 따라서 중복 여부는 파일 간 문구 유사성보다 같은 소비 주체와 같은 실행 시점에 실제로 함께 로드되는지를 기준으로 판단해야 한다.
- GPT-5.6 공식 지침은 안전한 범위와 승인 경계를 간결하게 한 곳에서 정의하고 같은 승인 지침의 반복을 피하도록 권고한다. 이는 반복 문구를 감사할 근거이지만, 로컬 정책·계약까지 자동으로 제거할 근거는 아니다.
- 현재 `skills/implement/SKILL.md`는 built-in `worker` 호출을 `model = "gpt-5.6-sol"`, `reasoning_effort = "high"`로 고정한다. `agents/analyzer.toml`과 `agents/verifier.toml`, `AGENTS.md`의 explorer 호출 계약도 각각 `high`를 명시하지만 서로 다른 소유 위치에 있다.
- 2026-08-28 Codex 최신 관련 이력 `e1fb167`은 agent 역할 경계를 정리했고, Claude 최신 관련 이력 `c087bab`은 하네스 중복 축소와 경로 기반 feature 문서 규칙 분리를 적용했다.

### 근거의 한계

- 저장소 문서와 공개 문서만으로 모든 main·subagent 하네스의 전체 시스템 지침을 동일하다고 단정할 수 없다. 설정 감사는 공식 지원 범위, 현재 실행에서 확인한 로딩 결과, 소비 주체별 관찰을 구분해야 한다.
- 현재 입력에는 특정 지침을 제거한 상태와 유지한 상태의 대표 작업 비교 결과가 없다. 이 설계는 그런 증거가 없을 때 제거 결론을 내리지 않고 `검증 필요`로 남기는 감사 계약을 정한다.

## 1. 구조

### 1.1 소유권 경계

변경은 기존 소유권을 유지한 세 문서 안에서만 이뤄진다.

- `AGENTS.md`는 요청을 `Per-Request`와 `Phased`로 분류하는 전역 진입 기준을 소유한다. 완료·검증 단위의 개수는 분해 기준으로만 쓰고, 그 자체를 `Phased` 권장 조건으로 쓰지 않는다. 이는 전역 분류 단계에서 불필요한 문서 phase 진입을 줄여 `SPEC §5.1`을 충족한다.
- `skills/config-review/SKILL.md`는 설정 지침의 중복·과잉 여부를 판정하는 감사 기준과 근거 부족 시 처리 방식을 소유한다. 하네스 중복과 모델 역량 보상형 지침은 별도 감사 관점으로 추가하되 기존 역할·권한, 흐름·상태, 문구·컨텍스트 기준을 대체하지 않는다. 이는 `SPEC §5.2`를 충족한다.
- `skills/implement/SKILL.md`는 built-in `worker`의 모델·추론 수준을 포함한 호출 계약을 소유한다. 이 파일의 worker 추론 수준만 `medium`으로 바꾸고 모델, 이력 전달, 실패 처리와 반환 계약은 유지해 `SPEC §5.3`을 충족한다.

### 1.2 책임 분리

- main은 기존과 같이 `Phased` 권장 여부 설명, 사용자 선택 확인, worker 호출과 최종 보고를 담당한다.
- `config-review`는 읽기 전용 감사만 수행한다. 대표 작업 증거가 부족하면 필요한 비교 조건을 보고할 수 있지만 설정을 수정하거나 제거를 확정 적용하지 않는다.
- built-in `worker`는 확정된 단일 Task 또는 `Per-Request` 변경만 구현한다. 추론 수준 조정은 worker의 역할·권한·중단 기준을 바꾸지 않는다.
- analyzer와 verifier, explorer의 현재 모델·추론 수준은 유지한다. 다른 agent·skill의 모델 또는 추론 수준도 변경하지 않는다.
- 새 설정 계층, 저장 형식, runtime hook, 경로 glob 규칙은 추가하지 않는다.

### 1.3 설정 배치

`skills/config-review/SKILL.md`의 `## 감사 기준` 아래에 `### 하네스와 모델 적합성`을 추가한다. 이 기준을 `AGENTS.md`에 두지 않는 이유는 전역 실행 정책이 아니라 `config-review`가 호출된 때만 필요한 감사 절차이기 때문이다. skill의 점진적 로딩 경계와도 일치한다.

## 2. 데이터 흐름

### 2.1 요청 분류 흐름

1. main은 사용자 요청과 적용 중인 `AGENTS.md`를 읽는다.
2. 사용자가 `Phased`, 특정 phase skill, 단계별 문서 작성 또는 기존 feature 진행을 명시했으면 현재의 명시 진입 규칙을 그대로 따른다.
3. 명시 진입이 아니면 다음 중 하나가 실제로 필요한지 판정한다.
   - 여러 설계 선택지 중 하나를 구현 전에 확정해야 한다.
   - 공개 API 규약·데이터 이전처럼 되돌리기 어려운 외부 영향의 판단 근거를 문서화해야 한다.
   - 완료 조건이나 영향 범위를 이후 단계에서 확인할 수 있도록 문서로 고정해야 한다.
4. 위 조건이 있으면 이유, 영향과 예상 산출물을 설명하고 `Phased` 선택을 확인한다.
5. 완료·검증 단위가 여러 개라는 사실만 있고 위 조건이 없으면 `Phased`를 권장하지 않는다. 요청을 독립적인 완료·검증 단위로 나눠 `Per-Request` 흐름에서 진행한다.
6. 분류 결과를 바꾸는 요구사항 해석이 미확정이면 기존 질문 기준에 따라 확인하고, 단위가 많다는 이유만으로 질문이나 phase 문서 생성을 추가하지 않는다.

이 흐름은 구조·책임·데이터 흐름 변경이라도 설계 선택이 이미 확정돼 있고 되돌리기 어려운 외부 영향이나 문서 고정 필요가 없다면 단위 수만으로 `Phased`에 진입하지 않게 한다. 동시에 실제 설계 결정이나 장기 추적이 필요한 요청의 문서 우선 흐름은 보존한다(`SPEC §5.1`).

### 2.2 설정 감사 흐름

1. 감사 대상 지침마다 그 지침을 소비하는 주체, 모델, 호출 경로와 로딩 시점을 식별한다.
2. `AGENTS.md`, 선택된 `SKILL.md`, agent 설정, 호출 메시지, 확인 가능한 시스템·developer 하네스 중 어떤 계층이 같은 실행에 들어오는지 기록한다.
3. 공식 문서가 보장하는 범위와 현재 실행·로그에서 관찰한 범위를 구분한다. main에서 관찰한 하네스 동작을 근거 없이 subagent에도 적용하지 않는다.
4. 후보 지침을 다음과 같이 분류한다.
   - 역할·권한·출력 형식·부작용 제한·프로젝트 관례처럼 사용자가 정한 정책 또는 계약
   - 같은 소비 주체의 하네스가 같은 의미와 강도로 이미 강제하는 중복 후보
   - 이전 모델의 반복 실패를 막기 위해 추가됐을 가능성이 있는 역량 보상형 후보
5. 하네스 중복 후보는 같은 소비 주체와 같은 로딩 범위에서 하네스가 동일 행동을 실제로 강제할 때만 성립한다. 하네스보다 좁거나 강한 로컬 예외, 적용 시점이 다른 규칙, 하네스를 공유하지 않는 agent용 규칙은 중복으로 판정하지 않는다.
6. 역량 보상형 후보는 그 지침이 막으려던 기존 실패 가설을 Git 이력, 실제 세션, 기존 이슈 또는 사용자 근거로 명시한다. 실패 가설을 복원할 수 없으면 추정임을 표시한다.
7. 축소·제거 판단에는 후보가 지키는 행동을 직접 드러내는 비파괴 대표 작업과 기대 결과가 필요하다. 가능한 경우 같은 모델·추론 수준·하네스·도구·권한·입력을 유지하고 후보 지침의 포함 여부만 바꾼 비교 결과를 사용한다.
8. 동일 조건의 기존 실행 근거가 있으면 대표 작업 증거로 사용할 수 있다. 조건이 다르거나 결과가 관찰 가능한 행동을 검증하지 못하면 증거로 일반화하지 않는다.
9. 실제 로딩 범위와 대표 작업 비교가 모두 제거 안전성을 뒷받침할 때만 `축소/제거 후보`로 제안한다. 증거가 없거나 실패 가설이 대표 작업에서 검증되지 않았으면 `검증 필요`로 보고하고 현재 지침을 유지한다.
10. 감사 결과는 기존 전체 판정과 역할 프롬프트 판정 안에 통합한다. 관련 발견에는 소비 주체, 실제 로딩 범위, 후보 유형, 기존 실패 가설, 대표 작업·기대 결과, 비교 결과와 `유지`·`축소/제거 후보`·`검증 필요` 처분을 포함한다.

이 흐름은 문구가 반복된다는 사실이나 GPT-5.6의 일반 역량만으로 지침을 제거하지 않고 실제 소비 범위와 관찰 가능한 행동을 근거로 판정하게 한다(`SPEC §5.2`).

### 2.3 worker 호출 흐름

1. main은 기존 `implement` 진입 조건으로 `Phased` Task 하나 또는 범위가 확정된 `Per-Request` 요청 하나를 선택한다.
2. built-in `worker`를 `model = "gpt-5.6-sol"`, `reasoning_effort = "medium"`으로 호출한다.
3. worker는 기존과 동일한 기준 문서, 최소 대화 이력, 위임 경계와 반환 형식을 받는다.
4. `medium` 호출을 적용할 수 없거나 호출이 실패하면 기존 계약대로 문서와 Task 상태를 유지하고 오류와 영향을 보고한다. 다른 모델·추론 수준이나 main 직접 구현으로 대체하지 않는다.
5. 구현 뒤 독립 검증과 상태 전환 흐름은 그대로 유지한다.

worker의 추론 비용만 낮추고 analyzer·verifier·explorer의 설계·검증·조사 품질 설정은 유지한다(`SPEC §5.3`).

## 3. 인터페이스

### 3.1 `AGENTS.md` 분류 계약

`## 문서 우선 흐름`의 진입 문구는 다음 의미를 고정한다.

- 일반 구현의 기본값은 한 번의 제한된 변경과 검증으로 끝나는 `Per-Request`다.
- `Phased` 권장은 구현 전에 설계 선택을 확정해야 하거나, 되돌리기 어려운 외부 영향의 근거를 남겨야 하거나, 완료 조건·영향 범위를 문서로 고정해야 할 때만 발생한다.
- 완료·검증 단위가 여러 개인 것만으로는 `Phased`를 권장하지 않고 독립 단위로 나눠 진행한다.
- 사용자가 명시적으로 선택한 `Phased`와 기존 feature의 승인 상태를 이어가는 규칙은 유지한다.

구조·책임·데이터 흐름·주요 설계라는 대상 종류만으로 진입시키지 않고, 그 대상에 구현 전 선택 확정이 실제로 필요한지를 판정하도록 바꾼다. 이 구분이 `SPEC §5.1`의 사용자 관찰 결과다.

### 3.2 `config-review` 감사 계약

새 감사 기준의 입력은 기존 감사 대상과 권위 문서에 더해, 관련 후보가 있을 때 다음 근거를 사용한다.

- 지침의 소비 주체와 모델
- 실제 instruction chain과 skill·agent 호출 시 로딩 범위
- 하네스가 보장하거나 현재 실행에서 관찰된 행동
- 역량 보상형 지침이 막던 기존 실패 가설
- 후보 행동을 확인할 대표 작업, 사전에 정한 기대 결과와 비교 실행 근거

근거가 일부 없더라도 전체 감사를 중단하지 않는다. 해당 후보만 `검증 필요`로 분류하고 부족한 근거와 그 영향을 출력한다.

관련 발견의 출력은 기존 우선순위별 발견 형식 안에서 소비 주체와 로딩 범위, 후보 유형, 기존 실패 가설, 대표 작업과 기대 결과, 비교 근거, `유지`·`축소/제거 후보`·`검증 필요` 처분을 추가한다.

이 계약은 정적 문구 비교를 발견의 출발점으로는 허용하지만 최종 축소 근거로는 허용하지 않는다. 정책·계약형 지침은 모델이 스스로 수행할 수 있다는 이유만으로 역량 보상형 후보로 분류하지 않는다(`SPEC §5.2`).

### 3.3 `implement` worker 호출 계약

호출 계약에서 바뀌는 값은 하나다.

```text
model = "gpt-5.6-sol"
reasoning_effort = "medium"
```

`fork_turns`, 호출 메시지 필수 경로, `blocked` 처리, 대체 금지와 완료 보고 형식은 그대로 유지한다. `agents/analyzer.toml`, `agents/verifier.toml`, `AGENTS.md`의 explorer 호출 계약은 인터페이스 변경 대상이 아니다(`SPEC §5.3`).

### 3.4 외부 인터페이스와 저장 경계

- 공개 API, 데이터 스키마, 파일 형식, 외부 서비스 연동은 없다.
- 세 파일은 Markdown 지침의 권위 위치를 그대로 유지하며 새 설정 파일이나 상태 저장소를 만들지 않는다.
- `config-review`의 새 처분 값은 감사 보고 안의 설명 라벨이며 machine-readable 공개 규약이나 영속 상태가 아니다.

## 4. 영향 범위

### 4.1 직접 변경

- `AGENTS.md`: `Phased` 권장 조건을 구현 전 설계 선택, 되돌리기 어려운 외부 영향, 완료 조건·영향 범위 문서화 필요로 좁히고 완료·검증 단위가 여러 개인 경우의 독립 단위 분해 기준을 추가한다(`SPEC §5.1`).
- `skills/config-review/SKILL.md`: `하네스와 모델 적합성` 감사 기준과 근거 부족 시 `검증 필요` 처리를 추가한다. 일반 구현 대화의 전역 컨텍스트는 늘리지 않는다(`SPEC §5.2`).
- `skills/implement/SKILL.md`: built-in `worker`의 `reasoning_effort` 한 값만 `high`에서 `medium`으로 바꾼다(`SPEC §5.3`).

### 4.2 확인 의존 관계

- `agents/analyzer.toml`, `agents/verifier.toml`, `AGENTS.md`의 explorer 모델·추론 수준은 변경하지 않는다.
- 관련 문구 검색은 worker의 `medium` 변경이 `skills/implement/SKILL.md`에만 생기고 analyzer·verifier·explorer 값이 유지되는지 확인할 수 있어야 한다.
- Git diff는 승인 범위인 세 파일 외에 Claude 설정, hook, agent 설정, runtime 설정이 바뀌지 않았음을 드러내야 한다.
- 루트 `README.md`의 구조·기능 설명은 바뀌지 않으므로 동기화 대상이 아니다.

### 4.3 제외 경계

- Claude `rules/feature-docs.md`와 같은 경로 glob 규칙
- `hooks.json`의 `PostCompact`와 Orca 백엔드
- Claude 전용 model, plugin, permission, agent frontmatter
- analyzer, verifier, explorer의 모델 또는 추론 수준
- 대표 작업 실행 자동화용 새 harness, eval 저장소 또는 신규 workflow

## 5. Decision Points

### 5.1 `Phased` 진입 기준의 축소 방식

**채택안**

현재의 대상 나열형 조건을 구현 전 결정 필요성 중심의 세 조건으로 좁히고, 완료·검증 단위가 여러 개인 경우에는 독립 단위로 나눠 진행한다는 별도 기준을 둔다.

**근거**

- 단위 수는 작업 분해 문제이지 설계 문서 필요성을 직접 뜻하지 않는다.
- 구현 전에 선택해야 할 설계 대안, 되돌리기 어려운 외부 영향, 이후 확인할 문서 기준은 대화가 끊겨도 판단 근거를 보존해야 하므로 `Phased`의 실익이 있다.
- Claude 최신 정리 방향과 `SPEC §5.1`이 같은 구분을 요구한다.

**배제한 주요 대안**

- 여러 단위가 있으면 계속 `Phased`를 권장하면 진행 상태 추적은 쉽지만 명확하고 되돌릴 수 있는 작업도 문서 세 단계를 거친다.
- 모든 구현을 `Per-Request`로 처리하면 단순하지만 구현 전에 확정해야 할 설계와 되돌리기 어려운 변경의 판단 근거가 대화에만 남을 수 있다.

### 5.2 하네스 중복과 역량 보상형 지침의 판정 방식

**채택안**

`config-review`에 별도 `하네스와 모델 적합성` 기준을 두고, 실제 소비 주체별 로딩 범위 확인과 기존 실패 가설, 통제된 대표 작업 비교를 요구한다. 근거가 부족하면 제거 제안 대신 `검증 필요`로 남긴다.

**근거**

- 같은 문구라도 main과 subagent의 하네스가 다르거나 skill 로딩 시점이 다르면 실제 중복이 아닐 수 있다.
- GPT-5.6 공식 지침은 반복 축소의 방향을 뒷받침하지만, 로컬 정책·계약의 삭제를 보장하지 않는다.
- 역량 보상형 지침의 필요성은 문구나 모델 세대만으로 확정할 수 없고 그 지침이 막던 실패를 대표하는 작업 결과가 필요하다.

**배제한 주요 대안**

- 문구 유사성이나 GPT-5.6 일반 권고만으로 제거 후보를 확정하면 소비 주체가 다른 필수 규칙을 잘못 제거할 수 있다.
- 모든 반복 지침을 유지하면 안전하지만 현재 모델에서 불필요한 하네스 중복을 계속 로드한다.

### 5.3 worker 추론 수준 변경 위치

**채택안**

`skills/implement/SKILL.md`의 built-in `worker` 호출 계약에서 `reasoning_effort`만 `medium`으로 바꾼다.

**근거**

- worker 호출 계약의 현재 소유 위치가 이 skill이므로 전역 모델 설정이나 agent 설정을 건드릴 필요가 없다.
- 승인된 Task·설계와 독립 검증 흐름이 구현 판단의 경계를 제공하므로 구현 실행 역할만 비용을 낮추고 설계·검증·조사 역할의 `high`를 유지할 수 있다.

**배제한 주요 대안**

- 전역 추론 수준이나 모든 agent의 값을 낮추면 요청 범위 밖 역할까지 영향을 준다.
- worker 모델까지 바꾸면 별도 품질 판단이 필요하고 `SPEC §5.3`을 위반한다.

### 5.4 Claude 설정의 선별 적용 경계

**채택안**

Claude 설정은 분류 기준과 감사 관점의 비교 근거로만 사용하고, Codex에서 이미 소유자가 정해진 세 문서 안에 의미를 옮긴다. 경로 glob, hook, backend와 Claude 전용 frontmatter는 이식하지 않는다.

**근거**

- Codex의 전역 `AGENTS.md`와 선택된 skill의 로딩 경계만으로 목표를 달성할 수 있다.
- 제외된 Claude 기능은 이번 세 완료 조건에 필요하지 않으며 별도 runtime·로딩 체계를 추가한다.

**배제한 주요 대안**

- Claude의 경로 glob 규칙이나 `PostCompact`와 backend 설정까지 맞추면 이번 완료 조건과 무관한 로딩·runtime 변경과 검증 비용이 추가된다.

남은 미확정 Decision Point는 없다.
