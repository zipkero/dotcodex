# Context Restore

## 목적

- 프로젝트 루트의 `CONTEXT.md`에서 저장된 작업의 현재 위치를 복원한다.
- 연결된 원본 문서를 확인해 오래되거나 어긋난 맥락을 그대로 이어가지 않는다.

## 적용 경계

- `CONTEXT.md`와 관련 프로젝트 문서를 읽어 복원 결과를 보고하는 작업으로 한정한다.
- Phased 문서가 있으면 Task 상태, 요구사항과 구현 계획은 해당 문서를 기준으로 복원한다.
- Phased 문서가 없는 Per-Request 맥락은 저장된 요청 범위와 현재 작업 트리를 기준으로 복원한다.
- `CONTEXT.md`는 작업을 중단시킨 설계 변경, 현재 논점과 다음 작업을 보완한다.
- `문서 반영 필요`에 기록된 확정 사항은 원본 문서보다 나중에 결정됐을 수 있으므로 단순 충돌로 폐기하지 않는다.
- `저장` 시각은 참고 정보로만 사용한다. 충돌의 우선순위나 어느 쪽이 최신인지 판정하는 근거로 사용하지 않는다.
- 프로젝트 루트는 `AGENTS.md`의 `프로젝트 루트` 기준으로 식별한다.
  하나로 결정할 수 없으면 사용자에게 대상 프로젝트를 확인한다.

## 복원 절차

1. 프로젝트 루트의 `CONTEXT.md`를 전체 읽는다.
2. 파일이 없으면 저장된 맥락이 없다고 알리고 추정으로 재구성하지 않는다.
3. `저장`이 없으면 이전 형식으로 보고 `저장 시점 없음`으로 복원한다.
   `현재 목표`, `현재 상태`, `다음 작업` 또는 완료 기준이 누락됐으면 누락된 내용을 기록하고 추정으로 채우지 않는다.
4. `현재 작업 문서`, `먼저 읽을 파일`과 `확정된 결정`에서 참조한 파일을 읽는다.
   `먼저 읽을 파일`이 없고 `먼저 읽을 문서`만 있으면 이전 형식으로 보고 같은 항목으로 읽는다.
5. 참조 파일이 없거나 `CONTEXT.md`와 원본 또는 Phased 문서가 충돌하면 그 차이를 먼저 보고한다.
6. Per-Request 맥락이면 저장된 변경 파일의 존재와 현재 내용을 확인한다.
   대상이 Git 저장소이면 저장된 branch·기준 `HEAD`와 현재 `git status`를 대조한다.
   `HEAD`가 저장 시점과 다르다는 사실만으로 충돌로 판정하지 않는다.
   저장된 변경이 사라졌거나 파일 상태가 설명과 어긋나면 차이를 보고한다.
   최신 결정의 확정은 사용자 판단 사항으로 남긴다.
7. `문서 반영 필요`에 명시되지 않은 충돌은 현재 원본 문서를 기준으로 복원한다.
8. `문서 반영 필요` 항목은 아직 원본에 반영되지 않은 확정 사항으로 복원한다.
   원본과 명시적으로 충돌하면 양쪽 내용을 함께 보고한다.
   현재 결정의 확정은 사용자 판단 사항으로 남긴다.
9. 현재 목표, 현재 상태, 현재 작업 문서, 확정된 결정, 미확정 판단, 다음 작업과 완료 기준을 짧게 복원한다.
10. 원본 문서의 미합의 구현 제안은 `미확정 판단`과 분리해 `관련 참고`로 짧게 소개한다.
   복원 단계에서 기술 대안을 확장하거나 사용자에게 선택을 요구하지 않는다.

## 복원 후 경계

- 복원은 읽기 전용으로 수행하며 파일, 문서, 코드, 설정과 작업 상태를 변경하지 않는다.
- `context-restore`만 요청받으면 복원 보고로 종료한다.
- 사용자가 다음 작업의 실행까지 명시하면 복원을 마친 뒤 `AGENTS.md`의 `문서 우선 흐름`과 해당 skill을 따라 진행한다.
- 복원 결과를 `CONTEXT.md`에 다시 기록하지 않는다.

## 복원 보고

다음 순서로 간결하게 보고한다.

1. 현재 목표
2. 저장 시점, 현재 상태, 현재 작업 문서와 먼저 읽을 파일
3. 확정된 결정
4. 미확정 판단
5. 저장된 다음 작업과 완료 기준
6. 누락되거나 원본 문서·현재 작업 트리와 충돌한 맥락
7. 관련 참고가 있으면 합의 여부와 함께 짧게 소개

`context-restore`만 요청받은 경우 복원 보고를 최종 산출물로 삼아 종료한다.
