# Project Init

## 목적
- `README.md`를 현재 프로젝트를 이해하고 사용하는 일반적인 진입점으로 생성하거나 재구성한다.
- 미래 계획의 기준점인 `ROADMAP.md`를 생성하거나 재구성한다.
- ROADMAP의 책임을 넘는 확정된 사용자 관점 정보와 기술 설계는 필요한 경우에만
  `docs/product.md`와 `docs/design.md`에 보존한다.
- 후속 기능 작업이 ROADMAP과 관련 `docs/**`를 기준 입력으로 사용하도록 문서 관계를 구성한다.
- 내용 없는 선택 문서와 기능별 문서는 만들지 않는다.

## 범위 판단
- 새 프로젝트의 최초 문서 작성, 루트 README·ROADMAP 초기화 또는 프로젝트 수준 문서 재구성에 사용한다.
- README 문구만 고치는 작고 명확한 변경은 Per-Request로 처리할 수 있다.
- 특정 기능의 요구사항 구체화, 공개 규약 변경 또는 여러 Task가 필요한 구현은 `spec-init`부터 시작한다.
- 기존 ROADMAP의 특정 마일스톤만 기능으로 구체화하려는 요청이면 `spec-init`이 필요하다고 보고한다.

## 대상 프로젝트 루트
- 프로젝트 루트는 `AGENTS.md`의 `프로젝트 루트` 기준으로 식별한다.
- 후보가 둘 이상이고 선택에 따라 산출물이 달라지면 작성 전에 질문한다.
- 프로젝트 루트를 확인하지 않은 채 현재 작업 디렉터리에 문서를 생성하지 않는다.

## 입력 조사와 정보 보존
- 기존 `README.md`, `ROADMAP.md`, `docs/`, 주요 manifest, 빌드·테스트 설정, 코드 구조와 사용자 입력을 먼저 확인한다.
- 의미 있는 기존 정보는 다음과 같이 분류한다.
  - 유지: 현재 문서의 책임과 맞고 계속 유효하다.
  - 이동: 다른 책임 문서에서 보존해야 한다.
  - 보류: 아직 확정되지 않아 ROADMAP 또는 후속 기능 문서에서 판단해야 한다.
  - 제거: 중복, 폐기된 결정 또는 사용자가 명시적으로 제외한 정보다.
- 문서를 축약하거나 재구성해도 계속 유효한 정보는 근거 없이 삭제하지 않는다.
- 이동한 정보는 새 문서에서도 원래 의미와 제약이 유지되는지 대조한다.
- 제거한 정보가 있으면 대상과 이유를 완료 보고에 포함한다.
- 최종 결과물, 핵심 사용자 또는 소비자, 목표 제공 수준, 프로젝트 완료 기준, 포함 범위 또는 보류 범위가
  여러 방향으로 해석되고 결과가 달라지면 작성 전에 질문한다.

## 산출물 선택
- `README.md`와 `ROADMAP.md`는 항상 존재해야 한다. 기존 내용이 이미 요청과 일치하면 변경하지 않고 검증만 한다.
- 다음 중 하나에 해당하는 확정된 사용자 관점의 상세가 있으면 `docs/product.md`를 생성하거나 갱신한다.
  - README·ROADMAP에 요약만 두면 의미 있는 사용자 동작이나 정책이 유실된다.
  - 상세 내용을 README·ROADMAP에 두면 문서 책임을 침범하거나 중복이 생긴다.
  - 기존 `docs/product.md`가 해당 정보의 기준 문서다.
  - 사용자가 제품 정의 문서를 명시적으로 요청했다.
- 같은 기준으로 아키텍처, 경계, 데이터·상태 흐름, 인터페이스, 실패 처리 또는 검증 방식의
  확정된 상세가 있으면 `docs/design.md`를 생성하거나 갱신한다.
- 상세 정보가 없으면 선택 문서를 빈 템플릿으로 만들지 않는다.
- 기존 선택 문서는 현재 입력에 상세가 없다는 이유만으로 삭제하거나 불필요하게 재작성하지 않는다.

## 공통 작성 규칙
- README는 현재 확인된 프로젝트만 설명하고, 아직 제공되지 않는 기능과 미래 계획은 ROADMAP으로 분리한다.
- ROADMAP과 선택 문서는 다음 세션에서 이전 대화 없이 읽어도 프로젝트 목표와 결정 기준을 복원할 수 있게 쓴다.
- 최종 목표, 현재 구현 상태와 제안된 계획을 명확히 구분한다.
- 기술 선택, 명령어와 현재 동작은 확인한 파일이나 실행 결과에 근거해서만 단정한다.
- 확인되지 않은 기능, 성능과 운영 보장을 현재 사실처럼 쓰지 않는다.
- 같은 정보의 상세본은 책임 문서 한 곳에 두고 다른 문서에서는 요약과 링크만 제공한다.
- README의 문서 섹션은 실제로 존재하는 ROADMAP과 선택 문서만 연결한다.
- 특정 제품 유형의 UI, 데이터 모델 또는 아키텍처를 입력 근거 없이 관례적으로 추가하지 않는다.
- 마일스톤은 사용자 또는 소비자가 확인할 수 있는 결과를 기준으로 묶고
  구현 계층이나 작업 단계로 나누지 않는다.
- 마일스톤 내부 구현 순서와 기능별 완료 조건은 후속 기능 문서에서 확정한다.
- 기능 후보는 후속 `spec-init`이 필요한 마일스톤에만 kebab-case로 제시하고 `features/`를 생성하지 않는다.
- 보류·제외 범위는 사용자가 언급했거나 최종 결과물과 직접 경계를 이루는 항목만 기록한다.
- 기존 문서의 기준을 바꾸는 갱신은 영향 범위를 먼저 보고한다.
  현재 요청이 기준 변경을 명시하지 않았으면 사용자 확인을 받는다.

## 문서별 기준

### README.md
README는 프로젝트 유형과 기존 관례에 맞는 현재 기준 안내 문서로 작성한다. 공통 섹션 이름을 강제하지 않는다.

- 프로젝트 이름과 현재 역할을 설명하는 짧은 소개
- 현재 사용할 수 있는 기능, 제공 범위 또는 저장소의 역할
- 프로젝트 유형에 맞는 확인된 시작 경로
  - 실행 가능한 앱·CLI: 설치, 빠른 시작과 사용 예
  - 라이브러리·SDK: 설치, 최소 연동 예와 API 문서
  - 설정·문서 저장소 또는 모노레포: 관리 범위, 구조와 탐색 경로
- 실제로 존재하는 ROADMAP과 선택 문서 링크
- 필요한 경우에만 전제 조건, 호환성·안정성 주의, 기여 방법과 라이선스

`현재 상태`를 관례적인 독립 섹션으로 만들지 않는다. 성숙도, 지원 중단 또는 호환성 상태가
사용자의 판단에 영향을 줄 때만 상단 안내나 적절한 섹션에 간결하게 표시한다.

아직 제공되지 않는 기능, 최종 목표, 마일스톤, 보류 범위, 상세 사용자 요구사항과 기술 설계는 넣지 않는다.

### ROADMAP.md
- 최종 결과물: 대상 사용자 또는 소비자, 핵심 가치, 목표 제공 수준과 완성 상태
- 프로젝트 완료 기준: 대상 사용자 또는 소비자가 최종 결과를 얻을 수 있음을 확인하는 관찰 가능한 조건
- 포함 범위: 최종 결과물에 포함되는 주요 기능 또는 산출물의 요약
- 마일스톤: 각 단계에서 완성되는 검증 가능한 결과, 의존 관계와 전환 기준
- 기능 후보: 해당 마일스톤을 후속 `spec-init`으로 구체화해야 할 때만 하나 이상 제시
- 최종 관문: 여러 마일스톤에 공통으로 필요한 정확성, 성능, 안정성, 접근성, 배포 또는 운영 조건이
  있을 때만 작성
- 보류·제외 범위: 제외 이유, 관련 위험과 재검토 조건

세부 UI 항목, 데이터 필드, 알고리즘과 Task 단위 구현 순서는 넣지 않는다.

### docs/product.md
프로젝트에 적용되는 항목만 선택한다.

- 문서 목적과 다른 프로젝트 문서와의 관계
- 대상 사용자, 문제와 핵심 사용자 흐름
- 사용자에게 관찰되는 기능별 동작과 상태
- 설정과 접근성
- 데이터 보관과 개인정보에 대한 사용자 관점의 정책
- 현재 목표 범위와 이후 후보

구현 계층, 시스템 API, 클래스 구조와 Task 단위 계획은 넣지 않는다.

### docs/design.md
프로젝트에 적용되는 항목만 선택한다.

- 문서 목적과 현재 구현·목표 설계의 구분
- 기술 방향, 아키텍처와 책임 경계
- 데이터와 상태 흐름, 저장 정책
- 내부·외부 인터페이스와 연동
- 실패 처리와 복구 경계
- 성능, 정확성, 안정성 검증 전략
- 주요 기술 위험, 대응과 미확정 결정

프로젝트 소개, 릴리스 마일스톤과 확인되지 않은 구현 세부사항은 넣지 않는다.

## 스킬 완료 조건
- 대상 프로젝트 루트가 확인되어야 한다.
- `README.md`와 `ROADMAP.md`가 요청, 현재 프로젝트 상태와 각 문서의 작성 기준에 맞아야 한다.
- 입력에서 계속 유효한 정보가 책임 문서 중 한 곳에 보존되어야 한다.
- 필요한 선택 문서만 존재하고 빈 섹션이나 템플릿 placeholder가 없어야 한다.
- 현재 구현, 목표와 제안이 구분되어야 한다.
- README의 문서 링크가 실제 산출물과 일치해야 한다.

## 완료 보고
- 확인한 프로젝트 루트와 판단 근거
- 생성·갱신하거나 변경 없이 검증한 파일과 문서별 책임
- 최종 결과물, 완료 기준, 마일스톤과 선택 문서 구성
- 이동·제거한 정보와 이유가 있으면 해당 내용
- 보류·제외 범위나 후속 기능 후보가 있으면 해당 내용
