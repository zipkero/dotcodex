# Config Review

## 목적
`AGENTS.md`, `README.md`, `.gitignore`, `.editorconfig`, `.gitattributes`, `docs/**`,
allowlist 관리 대상인 `agents/*.toml`, `skills/*/SKILL.md`와 존재하는 `skills/*/agents/openai.yaml`을
읽고 역할 프롬프트의 충분성, 책임 경계와 전역 정합성을 점검해 분석 결과만 보고한다.
요청 범위의 과도한 확장·제한, 판단 기준 부족, 절차 중복과 Codex 실행 모델에 맞지 않는 전제를 찾는 것이 목적이다.

## 컨텍스트 로딩
- 사용자가 특정 파일이나 skill을 대상으로 지정하면 해당 대상과 판단에 직접 필요한 참조만 읽는다.
- 사용자가 전역 감사 또는 전체 점검을 요청한 경우에만 `AGENTS.md`, 루트 `README.md`,
  `.gitignore`, `.editorconfig`, `.gitattributes`, `docs/**`, allowlist 관리 대상인 `agents/*.toml`과
  `skills/*/SKILL.md`, 존재하는 `skills/*/agents/openai.yaml` 전체를 읽는다.
- allowlist 관리 대상은 `.gitignore`의 추적 허용 규칙을 기준으로 판단한다.

## 공식 기준 참조
- 제품 버전에 따라 달라지는 Codex 동작, `AGENTS.md`, 프롬프트·컨텍스트 설계와 skill 책임은
  `openai-docs`를 통해 최신 공식 문서와 프롬프트 지침을 확인한다.
- 설계 배경이나 실증 근거가 필요할 때만 최신 OpenAI 블로그·Engineering·Research·System Card를 보조로 사용한다.
  게시일과 적용 대상을 확인하고 사례만으로 규칙을 일반화하거나 공식 문서를 대체하지 않는다.
- 중복, 모호한 표현, 파일 소유권, 로컬 문서 정합성처럼 현재 파일만으로 판단할 수 있는 항목에는
  외부 문서 조회를 요구하지 않는다.
- 출처 충돌은 현재 환경에서 검증된 동작, 최신 공식 문서, 보조 자료 순으로 판단하고 차이와 게시일을 보고한다.
  공식 자료도 사용자가 확정한 목적과 프로젝트 고유 제약을 자동으로 대체하지 않는다.

## 검토 우선순위
1. 역할 프롬프트 충분성
2. 책임 경계 명확성
3. 권위 위치와 소유권
4. 문서 우선 흐름 정합성
5. 중복 제거, 의미 보존 압축, 컨텍스트 상태

## 범위
- 역할 프롬프트 충분성
  - 각 `skills/*/SKILL.md`와 `agents/*.toml`이 자기 역할의 목적, 책임, 필수 입력, 성공 기준,
    판단·근거 기준, 출력, 중단 조건, 제외 범위와 충돌 규칙의 우선순위를 충분히 정의하는지 확인한다.
  - 실행 절차만 있거나 위 기준이 빠졌거나 역할 설명이 추상적이어서 핵심 판단을 모델 재량에 맡기면 `부족`으로 판단한다.
  - `SKILL.md` frontmatter의 `description`이 실제 호출 조건과 역할 범위를 충분히 드러내는지 확인한다.
  - `agents/openai.yaml`이 있으면 표시 정보, 기본 프롬프트, 호출 정책과 도구 의존성이 `SKILL.md`의
    역할과 호출 조건에 맞는지 확인한다.
- 책임 경계 명확성
  - 각 역할이 소유하는 결정과 소유하지 않는 결정을 구분하는지 확인한다.
  - main agent, subagent, skill 사이의 파일 수정 권한, 상태 전환 권한, 최종 판단 권한이 섞여 있지 않은지 확인한다.
  - 다음 단계로 넘기는 조건, 사용자 추가 요청이 필요한 조건, 중단해야 하는 조건이 구분되어 있는지 확인한다.
  - 다른 skill이나 agent의 소유 기준을 재정의하거나 암묵적으로 대체하는 문구를 발견 사항으로 보고한다.
- 문구와 구조 품질
  - 의미 충돌, 모호함, 중복, 의미 없는 부정형 반복과 폐기되거나 존재하지 않는 설명을 확인한다.
  - 조건, 예외, 권한과 중단 기준을 보존하면서 반복 문장, 긴 예시와 과한 배경을 압축할 수 있는지 확인한다.
  - 한 항목에 독립 규칙이 묶였거나 구체적인 예시·도구 나열이 원칙보다 커져 적용 범위를 좁히는지 확인한다.
  - 압축 뒤 실행 판단이나 역할·책임·근거 기준이 달라지면 제안하지 않는다.
  - 150칸 제한이 `features/**` 밖 Markdown 문서까지 확대되지 않았는지 확인한다.
- 성능 영향 판단
  - 규칙의 수, 길이, 엄격함이나 정적 문구만으로 모델의 추론이 약화된다고 판단하지 않는다.
  - 권한·범위·질문·보고 형식 제한과 문제 해결 방법·대안 탐색·판단 재량 제한을 구분한다.
  - 질문 빈도, 중단 시점, 변경 범위처럼 관찰 가능한 행동이 요청 수행을 불필요하게 막을 때만 성능 문제로 보고한다.
- 변경 제안 판단
  - 현재 설정보다 실제 행동, 판단 명확성이나 유지보수성이 나아질 때만 변경을 제안한다.
    명확한 규칙을 모호하게 만들거나 판단 비용과 이론적 유연성만 늘리는 변경은 제외한다.
- 권위 위치 불일치
  - `AGENTS.md`는 전역 원칙과 문서 우선 흐름의 기준만 소유한다.
  - `docs/languages.md`는 언어별 작업 기준의 진입점만 소유하고, 세부 기준은 `docs/languages/*.md`가 소유한다.
  - `agents/*.toml`은 custom subagent의 역할, 모델·추론·sandbox 성격, developer instructions를 소유한다.
  - phase별 실행 절차는 각 `skills/*/SKILL.md`가 소유한다.
  - 테스트 Task 작성 범위는 `implement-init`, 테스트 코드 작성 범위는 `implement`가 소유한다.
  - 분석 승인 기준은 `verify-analysis`, 구현 승인 기준과 Task 완료 후처리는 `verify`가 소유한다.
  - README가 위 기준을 다시 정의하지 않고 현재 구조를 정확히 설명하는지 확인한다.
- 문서 우선 흐름의 단계 실행 기준
  - `AGENTS.md` §문서 우선 흐름과 각 phase skill, agent 라우팅, README 설명이 일치하는지 확인한다.
  - 일반 구현 요청을 먼저 Per-Request로 평가하고, 한 번의 제한된 변경과 검증으로 완료할 수 있는 요청을
    Per-Request로 진행하도록 기준이 일치하는지 확인한다.
  - 여러 독립 완료·검증 단위, 주요 설계의 선확정, 공개 API 규약·데이터 이전·되돌리기 어려운 외부 영향 또는
    완료 조건·영향 범위의 문서 고정이 필요한 작업은 Phased의 이유, 영향과 예상 산출물을 설명한 뒤
    사용자 선택을 확인하도록 규정하는지 확인한다.
  - 사용자가 명시적으로 선택했거나 특정 phase skill·단계별 문서·feature 경로를 요청한 작업과 기존 feature 후속 작업만
    Phased 흐름으로 진입하는지 확인한다.
  - analyzer는 문서 초안, verifier는 지정된 skill에 따른 읽기 전용 후보 판단만 수행하고,
    최종 승인·거절, 상태 전환과 검증 거절 후 재진입 순서는 main이 소유하는지 확인한다.
  - 작성·승인 분리, 선행 승인 요구, 상위 문서 변경의 하위 상태 무효화와 Issues가 가리키는 재진입 단계가 각 skill 사이에서 일치하는지 확인한다.
  - 검증 상세를 저장하는 별도 Markdown 문서를 만들도록 규정하지 않았는지 확인한다.
  - 사용자가 특정 단계나 산출물만 요청한 경우 해당 범위를 넘어 진행하지 않는지 확인한다.
  - 사용자가 선택한 Phased 작업의 구현이나 전체 완료 요청에서는 필요한 단계의 연속 진행을 불필요하게 막거나
    단계마다 승인을 요구하지 않는지 확인한다.
  - 결과를 실질적으로 바꾸는 미확정 판단, 확정된 범위나 설계의 변경, 되돌리기 어려운 결정,
    외부 영향이 있는 작업에서 사용자 확인 없이 진행하도록 쓰여 있지 않은지 확인한다.
- 구현 품질 가드 위치
  - 기본 설계 원칙은 `implement`가 소유한다.
  - 테스트 통과용 하드코딩, fixture 전용 특수분기, assertion 맞춤 동작 축소 금지는 `implement`에 있어야 한다.
  - 주석 작성 기준은 과도하게 보강하지 않고 현재 `implement` 기준과 충돌하지 않아야 한다.
- 문서 산출물 완결성
  - `analyze-init`이 다음 단계에서 설계를 다시 결정할 필요 없는 `analysis.md`를 만들고, `verify-analysis`가 SPEC 추적성과
    구조·흐름·인터페이스·영향 범위·설계 결정을 원본 코드·설정에서 직접 검증하는지 확인한다.
  - `implement-init`은 미매핑 `SPEC §5.N`을 조용히 넘기지 않고 Task 추가, 완료 조건 제거, 제외 범위 보류 중 하나로 결정하게 해야 한다.
  - 문서 우선 흐름이 중간에 끊겨도 다음 단계가 기존 문서와 사용자 지시만으로 재개될 수 있는지 확인한다.
  - `승인 전 확인`, 미해결 설계 결정, 설계 변경 필요, 검증할 변경 범위가 다음 단계에서 무시되거나
    대화 기억에만 의존하지 않는지 확인한다.
- 컨텍스트 상태 저하 신호
  - `AGENTS.md`가 전역 원칙보다 특정 skill의 실행 절차, 예시나 운영 상세를 길게 설명한다.
  - 같은 규칙이나 custom agent의 역할 지침이 `AGENTS.md`와 여러 `SKILL.md`에 반복 정의되어 있다.
  - `SKILL.md`가 자기 호출 조건 밖의 정책까지 설명한다.
  - 오래된 handoff, 임시 메모, 실험 기록이 공식 규칙처럼 남아 있다.
- Codex 실행 모델과 맞지 않는 역할·절차 전제
- `agents/*.toml` 필수 필드, 역할 범위, sandbox 설정, 지침 언어 기준 위반
- 사용자에게 보이는 한국어 문서와 작업 분류용 영어 메타데이터의 언어 기준 위반
- 사용자에게 보이는 설명, 보고 문장, 문서 본문에 불필요한 영어식 표현이 반복되는지 확인한다.
  파일명, 명령어, 식별자, 설정 키, skill 이름, frontmatter 값, 출력 형식의 고정 라벨은 예외로 둔다.
- README의 실제 구조·기능 설명 정확성
  - 폐기되었거나 존재하지 않는 기능·파일이 남아 있는지 확인한다.
  - 새로 추가된 docs, skill, 정책 소유 위치, 문서 구조가 누락되었는지 확인한다.
  - 링크와 예시가 현재 파일 구조와 맞는지 확인한다.

## 제외
- 요청 없는 자동 수정
- `AGENTS.md` 정책 체계나 새 워크플로우 설계 확장
- README에는 규칙 정합성 기준을 적용하지 않는다. 다만 README가 실제 구조와 기능을 정확히 설명하는지는 별도 항목으로 점검한다.
- 전역 설정 수정 제안이 README의 관리 대상, skill 목록, 정책 소유 위치 설명과 어긋날 수 있으면 README 동기화 필요성을 영향받는 파일에 함께 안내한다.
- 선호나 일반론만 근거로 한 문구 변경 제안

## 출력
- 요약
- 전체 판정: `정상`, `과함`, `부족`, `충돌` 중 하나로 적는다.
  역할 프롬프트가 불충분하면 충돌이 없어도 `부족`, 컨텍스트 상태가 나쁘면 충돌이 없어도 `과함`으로 판단한다.
- 역할 프롬프트 판정: 필요한 기준이 명확하면 `충분`, 일부가 약하면 `부분 부족`,
  역할이 추상적이거나 실행 기준 없이 모델 재량에 크게 의존하면 `부족`으로 적는다.
- 우선순위별 발견 사항
- 각 발견 사항에는 위치, 확인 근거, 현재 문제, 실제 또는 예상되는 행동 영향,
  유지하는 선택과 비교한 변경 실익, 제안 방향, 영향받는 파일, README 동기화 필요 여부를 포함한다.
- 필요한 경우 before/after 수정안을 제시하고, 압축 제안이면 보존되는 의미와 줄어드는 표현을 함께 적는다.
- 발견 사항이 없으면 그렇게 말하되, 확인한 파일 범위와 남은 리스크를 함께 적는다.
